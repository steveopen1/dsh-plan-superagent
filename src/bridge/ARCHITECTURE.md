# 架构：计划板 ↔ 引擎 的单一真相源

> 一句话：**板说「要做什么」，引擎说「做到哪一步了」，桥只负责把「要做什么」变成工单、
> 再把「做到了哪一步」变成证据。** 桥自己什么都不知道，也不持有任何任务状态。

## 三方职责（写死，不可越界）

| 角色 | 是谁的真相源 | 拥有什么 | 绝不做的事 |
| --- | --- | --- | --- |
| **板**（`plan.board.json`） | **任务真相源** | 任务树、状态、验收标准、scope、依赖、证据、备注 | 不执行任务；不假装知道工单跑到哪一步 |
| **引擎**（superagent 的 sqlite） | **执行真相源** | 工单、attempt、worker 报告、PR、CI | 不改任务定义；不自己决定下一个任务 |
| **桥**（`src/bridge/**`） | **无真相源**，只有单向同步 | 翻译（任务→Trigger）、发号、回写 | 不缓存任务状态；不替人改任务定义；不把引擎状态镜像成第二份板 |

桥的存在只有一个理由：**两边的真相源长得不一样，而人需要一条确定的、可审计的路径把它们对上。**

## 方向：只有两条，且各只有一个动作

```
        ┌──────────────── 板（任务真相源）────────────────┐
        │  status / acceptance / scope / deps / evidence │
        └───────▲──────────────────────────────┬─────────┘
                │ ② 结果回写                    │ ① 派发一个 ready 任务
                │ （done/blocked + evidence）   │ （Trigger）
        ┌───────┴──────────────────────────────▼─────────┐
        │              引擎（执行真相源）                │
        │   工单 / attempt / 报告 / PR / CI             │
        └────────────────────────────────────────────────┘
```

| 方向 | 唯一动作 | 触发者 | 落地方式 |
| --- | --- | --- | --- |
| 板 → 引擎 | **派发一个 ready 任务** | 桥的轮询循环 | `ctx.receive(trigger)`：一次一个任务 |
| 引擎 → 板 | **结果回写**（工单终态） | 桥的轮询循环 | `PlanStore.mutate()`：`status` + `evidence` |

**没有第三条路径。** 桥不写工单、不改引擎设置、不把引擎状态镜像成第二份板；
板也不直接指挥引擎，只有「某个任务是 ready」这一个事实被桥读走。

## 唯一写入来源清单（逐字段）

板的节点字段（`src/board/schema.ts` 的 `BoardNode`）：

| 字段 | 唯一写入者 | 备注 |
| --- | --- | --- |
| `title` / `acceptance` / `scope` / `note` / `deps` / `priority` / `parent` | **人**（面板 `plan_edit`、板工具 `task_update`） | 任务定义，桥只读 |
| `status = planned / ready` | **人** | 「可以做了」是人的判断，桥不自己把任务改成 ready |
| `status = doing` | **发号动作**：板工具 `plan_next`，或桥的派单 | 两者写的是同一个动作（发号），不是两份状态 |
| `status = done / blocked` | **桥的结果回写**（引擎→板） | 桥是唯一写者；`done` 必须带证据（L3 证据门由 `lintBoard()` 兜住） |
| `evidence` | **桥的结果回写**（引擎→板） | 桥只写引擎里真实存在的东西：工单号、结局、worker 报告摘要、其中的链接、执行目录 |
| `startedAt` / `updatedAt` | 随上面每一次状态写入 | |
| `version` / `digest` | `PlanStore.mutate()` | 板的乐观锁 |
| 事件流 `events.jsonl` / `ROADMAP.md` | `PlanStore.mutate()` | 每次写入都留痕 |

引擎侧（桥**只读**，从不写）——字段清单见 `contract.ts` 的 `BRIDGE_READS`（引擎升版时对照那张单子）：

| 对象 | 真相源 | 桥怎么读 |
| --- | --- | --- |
| 工单 / attempt / 报告 / PR / CI | **引擎** | `ctx.tickets.open()` / `ctx.tickets.get()` |
| Trigger / 线程 | **引擎** | `ctx.triggers.get()` / `ctx.threads.get()` |
| 策略、来源配置 | **引擎**（人通过引擎面板改） | `ctx.config('planboard')` |

桥私有的东西（不是任何一方的真相源，只是同步台账）：

| 台账 | KV 键 | 用途 |
| --- | --- | --- |
| 派单记录 `taskId → {attempt, triggerId, ticketId, endedAt, settledAt}` | `planboard-bridge:dispatched` | 幂等：同一 task 不会建第二张单 |
| 已收单工单 id | `planboard-bridge:settled` | 幂等：同一张单只回写一次 |
| reconcile 首次发现时刻 | `planboard-bridge:reconcile` | 「板上有 ready、引擎里没工单」的宽限计时 |

## 回环审查：桥里有没有「引擎→板→引擎」的双写路径？

**审查结论：审查前有一处真回环，已修；现在没有。**

回环长这样：引擎的结果写回板 → 板的 `updatedAt` 变了 → 桥把「人动过任务」误判成
「任务重新就绪」→ 桥再派一次 → 引擎再跑一次 → 又写回板 …… 板和引擎互相喂，停下来。

| 环节 | 审查前 | 现在 |
| --- | --- | --- |
| 判断「任务可以重派」的基准 | `task.updatedAt > entry.endedAt`（**工单结束**的时刻） | `task.updatedAt > entry.settledAt`（**桥收单写回**的时刻）；没有收单记录时才退回 `endedAt` |
| 为什么原来会成环 | 工单结束的时刻**早于**桥写回板的时刻，所以桥自己的写回（会 bump `updatedAt`）永远满足「比 endedAt 新」 | 桥写回板的时刻与 `settledAt` 是同一个值，`updatedAt > settledAt` 不成立 → 桥不会因为自己写回而重派 |
| 谁能让任务重新就绪 | 只有**人**：收单之后人又动了这个任务（`updatedAt` 真的变了） | 同左 |
| 收单后的落点 | `done` / `blocked`（都不在 `readyTasks()` 里） | 同左 |

另外两处也是「看起来像回路、其实不是」的地方，写在这里免得下次有人重新怀疑：

- **桥把任务标成 `doing`**：这是**发号动作**的一部分（和板工具 `plan_next` 写 `doing` 同一件事），
  不是把引擎的状态镜像回板。板上「谁在做什么」只有一个来源：发号。
- **结果回写把 `done`/`blocked` 写进板**：这是引擎→板的唯一路径，方向正确；回写之后任务
  不再是 ready，桥也不会再派它（除非人重新启用）。

## 单发号（L1）：桥自己限流，不靠引擎的 maxWorkers

板的发号语义是**同一块同一时刻只允许一个 doing 任务**（板工具 `plan_next` 的 L1 硬锁）。
以前桥一次把所有 ready 任务都派出去，靠引擎 `maxWorkers=1` 兜底——那是**配置维持的默契，
不是结构保证**：人把 maxWorkers 调大，板上就会同时出现多个 doing，
而 L1（单发号）、L4（漂移核对）、L7（越界拦截）全都以「当前 doing 任务」为基准，
三个门的判定基准就分裂了。

现在的规则（`src/bridge/watch.ts`）：

1. 派单前先看板上有没有 doing 任务（`doingTasks()`，口径与板工具 `plan_next` **完全一致**）；
   有就不派（这一轮只做收单与 reconcile）。
2. 没有 doing 时，只派**一个** ready 任务；派出去它立刻变 doing，锁随之被占住。
3. 第一个任务收卷（结果回写把状态落成 `done`/`blocked`）之后，下一轮才派第二个。
4. 派出去却始终没有工单的（策略不放行、评估没接受）：宽限期后这次尝试作废，
   任务从 `doing` 放回 `blocked` —— 不放回去的话，锁会被一个根本没有工单的任务一直占着，
   整块板就再也不会派单。

与 `maxWorkers=1` 的差别（不是回归）：以前第二个任务的工单会**立刻建出来**在引擎里排队，
现在等第一个任务收卷后再建。结果一样（第二个任务照样被做掉），区别是引擎里同时只有一张单。

## reconcile：板上有 ready、引擎里却没有工单

**触发条件**（三者同时满足）：

1. 板上有 ready 任务（`readyTasks()`：依赖已满足、状态 planned/ready）；
2. 引擎里没有它的**在途工单**（桥的台账里没有「还在飞」的尝试）；
3. 这个状态**持续超过宽限期 90 秒**（`RECONCILE_GRACE_MS`）—— 刚派发时工单还没落库是正常的，
   没有宽限期会天天误报。

另外两种情况**不算**异常，不计入：

- 板上有 doing 任务（L1 锁被占着，剩下的 ready 任务在排队等锁，是正常状态）；
- 该任务有在途尝试（正在飞，只是工单还没落库）。

**提示文案**（走引擎已有的健康条目机制 `ctx.report('planboard', …)`，不新造通道）：

> 板上有 N 个 ready 任务但引擎里没有对应工单，可能派发失败

它拼在健康条目的 detail 里（`N ready · M dispatched · …`），健康状态仍是 `ready`——
这是「要人看一眼」的提示，不是引擎故障，不该把状态脚本打成失败。
